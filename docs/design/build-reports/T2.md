- **`governance/lifecycle.py`** (6.1, 8.1):
  - `TRANSITIONS` is the whole state machine, including VERIFYING and rollback.

  - `ProposalLifecycle` implements `submit`, `supersede`, `auto_apply` (with the NOTICED state), `tick`, `verify` and `mark_stale`, each through an executor.

## 5. Deviations from the design
- **Routine slot tier 2:** if the preferred slot is not expiry-safe, I first use the latest safe in-hours tick before it, and only then pre-open. This follows the 6.3 text and its TTL-12h table row (10:00) rather than the pseudo-code, which would pick 09:45.
- **Urgent compositions** (P0, P1) carry only classes at least as urgent; routine compositions at a slot carry everything. The design does not say which classes ride together.
- **Notice:** P0 is exempt. P1 is not: under the `*` default, a customer-facing harm stop still waits 60 minutes.
- **Chain length:** the 1e-6 margin adds one step: 0.35 at max_shift 0.05 takes 8 steps, where the design says 7.
- **Velocity ledger** is kept in memory in `ReleaseTrain`; it can be rebuilt from proposal transitions but is not persisted.
- **"How many people hear a different variant"** in the dry run counts a lead as changed with probability `1 - prod_d(1 - TV_d)`, treating the dims as independent.
- **Rule kept as written but costly:** an urgent request that comes up outside approver hours is submitted at the next opening, not at night. On a 10-19, latency 30-240 policy that costs about 2 hours of MTTR for an evening incident. I followed 6.3 ("in-hours first"); changing it is one line in `choose_submit` if you want MTTR to win.

## 6. Known gaps and risks
- **No persistence:** there is no Postgres-backed `ProposalStore` and the overlay rows are not wired to the store. Lifecycle steps are not wrapped in database transactions.
- **Executor:** only the test `DirectExecutor` (`tests/e2e/gov_harness.py`) is used, so the code is untested with T1's real IntentExecutor. Requests left in SUBMITTING, AUTO_APPLYING or APPLYING after a transport error are left for T1's reconciler.
- **Not done from the M3 acceptance list:** the crash matrix for submit, apply and auto-apply; full public_01/02 runs with a probe-only learner; the 9.7 policy rows end to end.
- **Verification:** only the allocation check exists, as a pure function, and nothing is wired. Without a verifier, `verify()` leaves proposals in VERIFYING. The prompt, DID and schedule verifiers belong to T4.
- **Harm-gate hooks:** the re-check after 20h and at notice expiry, and the "credibly worse" control swap, are callbacks for T3. Until wired they always pass.
- **Detecting supervisor edits** is in the test harness only; it belongs to T1's config mirror.
- **Kestrel evening point:** the notice is moved to the next approver opening, but the 4.1 rule about the evening planning point is left to the stepper.
